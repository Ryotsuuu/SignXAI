System Working Logic

SignXAI — Handwritten Signature Verification Using Explainable AI. Complete technical explanation of how the system enrolls a signer, verifies a questioned signature, decides GENUINE / FORGED / INCONCLUSIVE, and explains that decision — for presentation and onboarding purposes.

v3 No pretrained model Runs fully offline Cross-platform

1. Overview

A signer enrolls 1–5 genuine signature samples. The system builds a statistical profile of that specific person's natural signature variation — not a general model trained on thousands of other people's signatures. When a new (questioned) signature arrives, it's compared against that profile using seven independent classical computer-vision comparison methods, fused into one similarity score, and judged against a threshold calibrated from that person's own samples. An optional local vision-language model can narrate the result in plain language — but it never makes the decision itself.

Core design principle: the system is built on two separate "brains" that never cross responsibilities. The decision engine (classical, deterministic, auditable) decides valid/invalid. The explanation layer (optionally an AI model) only narrates metrics the decision engine already computed. See Section 9 for why this split exists.

3. Enrollment Workflow

Enrolling a signer builds their personal statistical profile from 1–5 genuine samples. No external data is used at any point.

Key detail: the original decoded image is saved (not an already-processed version) — see Section 5's note on why re-preprocessing must happen exactly once, identically, every time an image is loaded.

4. Verification Workflow

Comparing against every enrolled reference and keeping the best match means a signer's natural style variation across sessions doesn't automatically count against them — only the single most-similar reference needs to explain the questioned signature.

Auto-rotating every signature to canonical horizontal would destroy that signal. Only genuine orientation errors (sideways photos, via EXIF) are corrected.

7. Similarity Fusion

engine.py::_score_against_ref() combines seven independent comparisons into one score:

score = w[ssim]*SSIM + w[iou]*IoU + w[hog]*HOG_cos + w[lbp]*LBP_cos
      + w[hu]*Hu_cos + w[dtw]*DTW_sim + w[scalar_profile]*ScalarProfile

default weights (hand-set, or population-calibrated — see Section 15):
  ssim=0.20  iou=0.12  hog=0.18  lbp=0.08
  hu=0.10    dtw=0.12  scalar_profile=0.20
ComponentMeasures
SSIMStructural similarity of the aligned pixel intensities
IoUInk-pixel overlap ratio after alignment
HOG cosineSimilarity of local stroke-direction patterns
LBP cosineSimilarity of local ink texture patterns
Hu cosineSimilarity of rotation/scale-invariant shape descriptors
DTW similarityDynamic-time-warped similarity of the stroke contour path
Scalar profileMean of exp(-|z|) across all ~20 scalar features, where z is how many standard deviations the questioned value is from this signer's own enrolled mean (see Section 8 for how std is estimated with few samples)

Before comparison, the questioned image is rigidly aligned (translation + rotation + scale, ORB feature matching + ECC refinement) to each reference in app/core/align.py, so incidental differences in how the page was photographed don't get mistaken for signature differences.

8. Threshold Calibration & Decision Logic

This is the core of "how does the system know if a NEW signature counts as this person's, given natural variation is expected" — and the part that received the most correction across v2/v3 development.

8.1 Per-writer mean/std

From all enrolled samples' scalar features, compute a per-feature mean and standard deviation — this signer's own natural range for each measurement, not a population average.

8.2 Threshold from intra-reference agreement

With 2+ references, every pair of enrolled references is compared against each other (using the exact same aligned scoring function used for real verification — a historical bug, v2 Bug #7, used a different, cruder formula for calibration than for verification, making the threshold not directly comparable to real scores). The resulting intra-reference scores establish a baseline: threshold = mean(intra) − 2·std(intra).

The core v3 fix (Bug #13): with exactly 2 references there is exactly ONE intra-reference comparison — and the standard deviation of a single number is always exactly zero. That gave the threshold zero slack for any natural variation at all. Fixed with a shrinkage estimator: blend the observed std toward a conservative, hand-set prior floor (not learned from any dataset) when few reference pairs exist, fading the prior out as more real references accumulate.

8.3 The symmetric uncertain band (Bug #14)

Originally, the "uncertain" zone only existed below threshold — any score above threshold was confidently GENUINE, no matter how close. Fixed to be symmetric: scores within the band on either side route to human review. This matters more once the threshold itself has honest uncertainty (from Section 8.2's fix) baked in.

8.4 Confidence score

A logistic function of the distance from threshold: far above threshold → confidence near 100%; right at threshold → confidence near 50%.

9. Explainable AI Layer

app/llm/report.py::generate_report() takes a completed verification case and produces a human-readable report through one of two paths:

Path A — Deterministic template

Always available, zero dependencies. Rule-based sentence generation directly from the metrics: which features deviated, by how much, grouped by category, with a methodology section, confidence explanation, and concrete recommendation. Cannot hallucinate — it only restates numbers that were already computed.

Path B — Local vision LLM

Optional (llama-cpp-python + GGUF model). Given the same metrics plus the actual evidence images, asked to narrate in plain language via a strict JSON schema. 3-attempt validation/repair loop; falls back to Path A on any failure.

Why the LLM never decides validity

A May 2026 study found vision-LLMs reasoning freely about skilled forgeries get more confidently wrong, not less — a "Rationalization Trap" where the model explains away real forgery artifacts as natural variation while reporting high false confidence. The JSON schema this system sends the LLM structurally has no field for overriding the verdict — it can only fill in narrative fields describing metrics the engine already froze.

Prompt engineering (v3)

The system prompt frames the model as writing for a non-technical reader, explicitly asks for substantive multi-sentence sections (not one-liners), and the JSON contract includes methodology, confidence_explanation, and recommendation fields alongside the original summary/findings/conclusion — producing a genuinely detailed (3-page PDF) report either way.

11. Online Feedback Loop

engine.py::feedback() lets an examiner confirm or correct a verdict after the fact. Confirming reinforces the current threshold; correcting nudges it — a lightweight statistical update, not gradient descent on a neural network. This is the system's "learns over time" mechanism from the original project brief, implemented without any external training data.

12. Hardware & GPU Selection

app/device.py::detect_device() probes the machine (RAM via psutil, GPU via nvidia-smi, Apple Silicon via platform arch) and recommends a GGUF model tier. On multi-GPU machines, the GPU with the most VRAM is selected automatically (an integrated GPU like Intel UHD Graphics is never returned by nvidia-smi at all, so it can never be mistakenly preferred over a discrete NVIDIA card). If a model is already downloaded, that one is used regardless of what hardware-tier logic would otherwise suggest, so status and load never disagree about which model is active.

17. Honest Limitations

(renumbered from v3's Section 16 — see the table above for v4-specific caveats)

  • Accuracy has only been validated on a 10-writer CEDAR sweep (20 verifications) — not a large-scale benchmark. See PROJECT_MEMORY_v8.md Section 4 for the exact numbers and their caveats.
  • With only 2 enrolled references, a meaningful fraction of verifications correctly route to INCONCLUSIVE rather than being auto-decided — enrolling 3-5 references improves this.
  • The heatmap is a pixel-divergence visualization, not literally Grad-CAM/SHAP (those require a differentiable model this classical pipeline doesn't have).
  • GPU offload logic is correct by inspection but not yet confirmed on real GPU hardware in this development environment.
  • Multi-script (non-Latin) signature generalization is architecturally reasoned (features are script-agnostic) but not empirically tested against real non-Latin samples.
